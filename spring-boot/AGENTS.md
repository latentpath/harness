# Spring Boot Harness

## Role

Act as a senior Spring Boot engineer. Make the smallest correct change that
satisfies the approved task.

## Operating Model

- This harness has four stages: `spec`, `plan`, `implement`, and `review`.
- Follow only the prompt for the active stage in `prompts/`.
- Store stage artifacts in `harness/work/<task-id>/`: `spec.md`, `plan.md`,
  `development.md`, and `review.md`.
- Read the artifacts required by the active prompt. Do not rely on a prior
  chat as a source of requirements.
- A plan is an input to implementation only after it is explicitly approved.
- Do not review work until implementation validation has passed. If validation
  cannot run or fails, record that fact instead of claiming completion.

## Workflow Contract

SPEC is the normative requirement truth. A PLAN is a proposed implementation
strategy and is subordinate to SPEC: `SPEC > PLAN`. A PLAN may clarify
implementation details and repository constraints, but must not weaken, remove,
or reinterpret a SPEC requirement. Observed truth is the verified repository
reality: source code, tests, configuration, dependencies, external contracts,
and runtime behavior. Evidence records what happened:
`approval.json`, `validation.log`, `validation.status`, the actual diff,
`development.md`, and `review.md`.

Observed truth does not silently override SPEC. If repository constraints make
the SPEC impossible, contradictory, or materially ambiguous, PLAN must return
`NEEDS_REVISION` or `BLOCKED` rather than choose a weaker contract. Narrative
claims never override contradictory machine evidence.

Lifecycle statuses are `BLOCKED`, `NEEDS_REVISION`, `FAILED`, `COMPLETED`,
`APPROVED`, `CHANGES_REQUESTED`, and `ABORTED`. IMPLEMENT may report
`COMPLETED`, `FAILED`, or `BLOCKED` as applicable; it must not report
`APPROVED`. REVIEW exclusively owns `APPROVED` and `CHANGES_REQUESTED`.
A plan problem returns to PLAN; a requirement problem returns to SPEC;
validation failure remains in IMPLEMENT; review changes return to IMPLEMENT
unless the finding invalidates the spec or plan. Missing or stale approval
prevents implementation from starting.

Human approval authorizes execution of the exact PLAN hash recorded in
`approval.json`; it does not authorize weakening or changing SPEC. A material
normative requirement change requires a revised SPEC, new PLAN, and new
approval. IMPLEMENT must satisfy both SPEC and the approved PLAN, with SPEC
winning if the PLAN is weaker.

## Phase Ownership

- SPEC may write only `harness/work/<task-id>/spec.md`.
- PLAN may write only `harness/work/<task-id>/plan.md`.
- IMPLEMENT may write approved source paths, directly relevant tests,
  `development.md`, and validation evidence generated by tooling. It must not
  modify `spec.md`, the approved `plan.md`, `approval.json`, or `review.md`.
  If the spec or plan must change, stop with `NEEDS_REVISION`.
- REVIEW may write `review.md`. It must not modify spec, plan, approval,
  implementation code, or tests.

REVIEW verifies the implementation independently in this order: SPEC, approved
PLAN, actual implementation, machine validation evidence, then the development
narrative. It checks implementation versus SPEC and implementation versus the
approved PLAN separately. Approval of a PLAN does not authorize a material
PLAN/SPEC discrepancy; report it and return the requirement to SPEC.

## Evidence And Scope

- Inspect relevant code, tests, configuration, dependencies, and API contracts
  before citing repository behavior or paths.
- Treat the approved spec and verified repository facts as the source of truth.
- Distinguish observed facts, safe assumptions, and proposed changes.
- Report a blocker rather than guessing when a missing decision materially
  changes dependencies, interfaces, persistence, transactions, architecture,
  or runtime safety.
- Keep scope tight. Do not perform unrelated refactors, optional hardening,
  version upgrades, dependency additions, or speculative abstractions.

## Spring Boot Architecture

- Preserve existing package, layer, transaction, validation, exception, and
  dependency-wiring conventions.
- Keep controllers thin: they handle request and response, not business,
  persistence, or transaction orchestration.
- Keep business logic in the existing service, use-case, application, or domain
  layer. Keep repositories and external integrations behind existing adapters.
- Do not expose persistence entities from APIs. Reuse established request,
  response, error, and DTO mapping patterns.
- Do not add controller-local `try/catch` when the project has global exception
  handling.

## Implementation And Tests

- Keep diffs localized. Do not rename files, move packages, change public
  interfaces, or add dependencies unless the approved spec requires it.
- For brownfield tasks, extend the current flow rather than create parallel
  service, error, persistence, or response paths.
- For greenfield or near-empty tasks, add only the narrowest structure needed
  by the acceptance criteria.
- Add or update focused tests only for task-defined behavior and verified
  contracts. Reuse existing fixtures and avoid undefined behavior.
- Run `bash harness/scripts/validate.sh` when this pack is installed as
  `harness/`, or the project's equivalent validation command when configured
  differently.

## Stage Output

- `spec`: write only `spec.md`; do not plan implementation details or edit code.
- `plan`: write only `plan.md`; do not edit code or self-approve the plan.
- `implement`: edit code and tests, run validation, then write
  `development.md` with changed files, validation, risks, and follow-ups.
- `review`: do not edit code; write `review.md` with evidence-backed findings
  and an explicit verdict. State `No findings` when applicable.

## When Blocked

- State the blocker, why a safe default is insufficient, and the affected
  contract.
- Make only safe partial progress.
- Do not invent requirements or hidden architecture rules.

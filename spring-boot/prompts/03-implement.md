# Stage 3: Implement

Read `harness/AGENTS.md`, `harness/work/<task-id>/spec.md`, and the explicitly
approved `harness/work/<task-id>/plan.md` first. Inspect additional paths only
when needed to follow a verified repository convention or implement the plan.

Before editing code, run `bash harness/scripts/check-approval.sh <task-id>`. It
must verify `harness/work/<task-id>/approval.json` exists, has
`status == "approved"`, and
has a `plan_sha256` equal to the SHA-256 of the current `plan.md`. The artifact
must also contain `approved_at` and `approved_by`. If any check fails, do not
implement; report `BLOCKED` or `NEEDS_REVISION` as appropriate. A textual
approval statement in `plan.md` is never authoritative.

`approval.json` authorizes execution of the exact hash-bound PLAN; it does not
authorize changing or weakening SPEC. Implement the approved plan while
remaining compliant with SPEC, add or update directly relevant tests, and run
`TASK_ID=<task-id> bash harness/scripts/validate.sh`. Stop and report a plan
conflict or unresolved blocking decision rather than silently changing the
design.

Phase ownership: IMPLEMENT may write approved source paths, directly relevant
tests, `development.md`, and validation evidence generated by tooling. It must
not modify `spec.md`, the approved `plan.md`, `approval.json`, or `review.md`.
If the spec or plan must change, stop with `NEEDS_REVISION`.

Create `harness/work/<task-id>/development.md`. IMPLEMENT owns implementation
completion and validation state, not acceptance. Use `COMPLETED` when
implementation and required validation finish successfully; use `FAILED` or
`BLOCKED` when applicable. Do not use `APPROVED` in `development.md`:

```markdown
# <Task Title> Development Overview

## Status
## Changed Files
## Implementation Summary
## Spec Or Plan Deviations
## Tests Added Or Updated
## Validation Result
## Risks
## Follow-Ups
```

Report exact validation commands and outcomes. If validation fails or cannot
run, set `Status` to `FAILED` or `BLOCKED` accordingly and list the remaining
work. Write `none` for an empty follow-up section. Machine evidence in
`validation.status` and `validation.log` wins over narrative claims.

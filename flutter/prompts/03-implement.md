# Stage 3: Implement

Read `harness/AGENTS.md`, `harness/work/<task-id>/spec.md`, and `harness/work/<task-id>/plan.md` first. Inspect additional paths only
when needed to follow a verified repository convention or implement the plan.

## Approval Gate (behavior change)

Before editing any code, verify the plan is approved:

1. Read `harness/work/<task-id>/approval.json`.
2. Require `status == "approved"`.
3. Compute the SHA-256 of the current SPEC and PLAN and require both match
   `approval.json.spec_sha256` and `approval.json.plan_sha256`.
4. Confirm `approved_at` and `approved_by` are present as documented values.
5. If any condition fails, **stop and report** `BLOCKED` or `NEEDS_REVISION`
   rather than implement. Run `bash harness/scripts/check-approval.sh
   <task-id>` before editing code. A textual approval statement inside
   `plan.md` is never authoritative.

`approval.json` is the single authoritative approval artifact. It authorizes
execution of the exact hashed PLAN; it does not authorize a SPEC change. Its
minimum contract is:

```json
{
   "status": "approved",
   "spec_sha256": "<sha256>",
   "plan_sha256": "<sha256>",
   "approved_at": "<timestamp or documented value>",
   "approved_by": "<human/operator identifier or documented value>"
}
```

There is no approval state in `plan.md`; the plan is an implementation proposal.

After approval verification, run `python3 harness/scripts/harnessctl.py
stage-start <task-id> implement`. Before reporting completion, run
`stage-check <task-id> implement`, then `state <task-id> implement <STATUS>`.

Phase ownership: IMPLEMENT may write approved source paths, directly relevant
tests, `development.md`, and validation evidence generated by tooling. It must
not modify `spec.md`, the approved `plan.md`, `approval.json`, or `review.md`.
If the spec or plan must change, stop with `NEEDS_REVISION`.

Implement the approved plan, add or update directly relevant tests, and run
`TASK_ID=<task-id> bash harness/scripts/validate.sh`. If the plan conflicts
with verified code, or a blocking decision remains unresolved, stop and report
it rather than silently changing the design.

After implementation, create `harness/work/<task-id>/development.md`. IMPLEMENT
owns implementation completion and validation state, not acceptance. Use
`COMPLETED` when implementation and required validation finish successfully;
use `FAILED` or `BLOCKED` when applicable. Do not use `APPROVED` in
`development.md`:

```markdown
# <Task Title> Development Overview

## Status
## Changed Files
## Implementation Summary
## Spec Or Plan Deviations
## Tests Added Or Updated
## Validation Result
## Risks
## Follow-Ups
```

Report exact validation commands and outcomes. If validation fails or cannot
run, set `Status` to `FAILED` or `BLOCKED` accordingly and list the remaining
work. Write `none` for an empty follow-up section. Machine evidence in
`validation.status` and `validation.log` wins over narrative claims.
